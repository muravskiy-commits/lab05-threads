Лабораторна робота №5: Потоки, Race Conditions та Mutex

1. Мета лабораторної роботи
Експериментально дослідити багатопотокову модель виконання програм у межах одного процесу за допомогою POSIX Threads (pthreads), проаналізувати спільну та локальну пам'ять потоків, відтворити стан гонитви (race condition) і втрату оновлень (lost update), виправити помилку синхронізації за допомогою mutex, дослідити виникнення та усунення deadlock, а також реалізувати паралельне обчислення суми без зайвих блокувань.

Головні питання лабораторної роботи:
Що станеться, якщо декілька потоків одночасно змінюють одну спільну змінну, і як правильно організувати безпечну та ефективну роботу зі спільною пам'яттю?

Завдання 1. Перший Thread (first_thread.c)
1. Скільки processes створила програма? Один процес (сам запуск виконуваного файлу).
2. Скільки threads існує після успішного pthread_create()? Два потоки: головний потік (Main Thread) та створений робочий потік (Worker Thread).
3. Яка функція виконується новим thread? Функція worker().
4. Для чого потрібен pthread_join()? Для синхронізації: головний потік призупиняє своє виконання і чекає, доки робочий потік завершить роботу, перш ніж закінчити програму.
5. Чи створює pthread_create() новий address space? Ні, на відміну від fork(), новий потік працює у тому самому адресному просторі процесу.

Аналіз та відповіді на питання:
1. Чи однакова адреса value для всіх потоків? Так, адреса ідентична в обох робочих потоках і в main().
2. Чому? Тому що всі потоки одного процесу поділяють спільний адресний простір (сегменти коду .text, глобальних даних .data/.bss та купу heap).
3. Чому фінальне значення value залежить від порядку виконання? Оскільки обидва потоки записують значення в ту саму комірку пам'яті, фінальний результат у main() визначається тим, який потік встиг виконати запис останнім (100 або 200).
4. Чому локальні змінні local мають різні адреси? Кожен потік отримує власний ізольований стек викликів (Thread Stack) для зберігання локальних змінних, аргументів функцій та адрес повернення, щоб потоки не перезаписували проміжні дані один одного.

Архітектура пам'яті багатопотокового процесу:
Process
├── Code (.text)      <- спільний
├── Data (.data/.bss) <- спільний
├── Heap              <- спільний
├── Thread 1 -> Stack 1 (власний)
└── Thread 2 -> Stack 2 (власний)

Пояснення Lost Update та аналіз машинного коду:
На рівні мови C запис counter++; виглядає як одна дія, але у згенерованому Assembly (race.s) він розкладається на три окремі машинні інструкції:
1. mov rax, QWORD PTR counter[rip] (READ: зчитування з пам'яті в регістр)
2. add rax, 1 (MODIFY: збільшення значення в регістрі)
3. mov QWORD PTR counter[rip], rax (WRITE: запис із регістра назад у пам'ять)

Оскільки ця послідовність не є атомарною (неподільною), планувальник може перервати потік між читанням і записом. Якщо Thread A і Thread B одночасно прочитають значення 100, обидва збільшать його до 101 і обидва запишуть 101 у пам'ять — один інкремент безповоротно втрачається (lost update).

Елементи Race Condition у програмі:
- Shared state: глобальна змінна counter
- Concurrent writers: thread1 та thread2
- Critical operation: інкремент counter++

Чому mutex виправив проблему:
М'ютекс (pthread_mutex_t) забезпечує взаємне виключення (mutual exclusion): у критичній секції між pthread_mutex_lock() та pthread_mutex_unlock() одночасно може перебувати лише один потік. Поки один потік виконує READ-MODIFY-WRITE, інший потік переводиться у стан очікування (block/wait), тому операції більше не перекриваються.

Де саме повинен бути Lock (Завдання 9):
Якщо винести pthread_mutex_lock() за межі циклу for (на всі 1 000 000 ітерацій), результат залишиться правильним (2000000), але зникне паралелізм (concurrency): перший потік захопить блокування на весь час циклу, а другий потік простоюватиме, доки перший повністю не завершить роботу. Критична секція повинна захищати лише мінімально необхідну ділянку роботи зі спільними даними.

Вартість синхронізації (time ./race проти time ./mutex_counter):

| Програма | Run 1 (real) | Run 2 (real) | Run 3 (real) |
| :--- | :---: | :---: | :---: |
| race | 0.008s | 0.007s | 0.008s |
| mutex_counter | 0.095s | 0.102s | 0.091s |

Синхронізована програма працює значно повільніше (у 10+ разів), оскільки на кожній із 2 000 000 ітерацій витрачається час на атомарні операції захоплення/звільнення замка, системні виклики ядра (futex) при конкуренції потоків (lock contention) та перемикання контексту.

Завдання 11. Більше Threads (race_four.c, mutex_four.c)

Порівняння конфігурацій для сумарних 2 000 000 інкрементів:
- 2 threads without mutex: швидке виконання (~0.008s), некоректний результат (~1.1–1.4 млн).
- 4 threads without mutex: ще більша втрата оновлень (~0.7–1.0 млн) через вищу конкуренцію між 4 потоками.
- 2 threads with mutex: стабільно 2000000, час виконання ~0.095s.
- 4 threads with mutex: стабільно 2000000, але час виконання зростає до ~0.180–0.220s.

Висновок: Більша кількість потоків не робить програму автоматично швидшою. Якщо всі потоки постійно змагаються за один спільний м'ютекс (високий lock contention), вони фактично вишиковуються в чергу, а накладні витрати на планування та синхронізацію лише сповільнюють виконання.

Завдання 12 та 13. Shared Heap Memory та Thread Return Value (shared_heap.c, thread_result.c)
1. Де знаходиться data у shared_heap.c? У динамічній пам'яті (heap), оскільки виділена через malloc().
2. Чи бачить worker ту саму область пам'яті? Так, вказівник data передається як аргумент у worker(), обидва потоки виводять однакову адресу в купі, і зміна data->value += 10 видима у main().
3. Що змінилося б при одночасному записі кількох потоків у data->value? Виникла б та сама race condition, що й зі змінною в глобальній пам'яті, оскільки heap також є спільним для всіх потоків.
4. Чому у thread_result.c не можна повертати адресу локальної змінної (&result)? Локальна змінна створюється на власному стеку робочого потоку. Після завершення функції calculate() кадр стеку цього потоку знищується, і повернутий вказівник стає висячим (dangling pointer) — звернення до нього у main() призводить до невизначеної поведінки (Undefined Behavior). Виділення пам'яті в heap через malloc() гарантує, що об'єкт житиме до явного виклику free() у main().

Завдання 14, 15, 16 та 17. Deadlock та порівняння з Race Condition (deadlock.c)

Схема виникнення взаємного блокування (Deadlock):
Thread 1 захоплює mutex1 -> спить 1с -> чекає на звільнення mutex2
Thread 2 захоплює mutex2 -> спить 1с -> чекає на звільнення mutex1
Результат: утворюється циклічне очікування (Circular Wait) — жоден потік ніколи не продовжить роботу.

Виправлення у deadlock.c:
У функції worker2() змінено порядок захоплення блокувань на ідентичний до worker1(): спочатку pthread_mutex_lock(&mutex1), потім pthread_mutex_lock(&mutex2). Це розриває цикл очікування (усуває умову Circular Wait), і програма успішно завершується.

Порівняння Race Condition та Deadlock:

| Характеристика | Race Condition | Deadlock |
| :--- | :---: | :---: |
| Threads продовжують execution? | Так | Ні (зависають назавжди) |
| Результат може бути неправильним? | Так | Так (результат взагалі не досягається) |
| Програма може повністю перестати прогресувати? | Зазвичай ні | Так |
| Пов'язано з timing/order? | Так | Так |
| Mutex може допомогти? | Так (забезпечує mutual exclusion) | Ні (сам по собі не вирішує) |
| Неправильне використання mutex може бути причиною? | Ні (причина — відсутність захисту) | Так (різний порядок lock або забутий unlock) |

Thread 4: 218750125000

Архітектурний аналіз parallel_sum.c:
1. Shared data: масив структур tasks[4], виділений у main(), до елементів якого звертаються потоки.
2. Thread-local data: локальний акумулятор long sum усередині calculate_sum(), який знаходиться на власному стеку кожного потоку.
3. Чому потоки не потребують mutex у циклі? Кожен потік читає лише свій неперетинний діапазон [start, end], накопичує суму у власній локальній змінній і наприкінці записує результат у власну комірку tasks[i].result — конфлікту запису (shared mutable state) немає.
4. Коли main читає результати? Тільки після завершення pthread_join() для всіх 4 потоків, що гарантує готовність усіх часткових сум.
5. Чому цей підхід кращий за спільний лічильник із м'ютексом? Повністю усуваються накладні витрати на мільйон блокувань і розблокувань (lock contention), тому потоки працюють по-справжньому паралельно на різних ядрах CPU.
6. Коли паралелізація має сенс (порівняння з sequential_sum)? Для малих N (наприклад, 1 000 000) накладні витрати на створення 4 потоків (pthread_create) можуть перевищувати виграш від поділу обчислень. Паралелізація стає ефективною, коли обсяг обчислень у кожному потоці значно більший за витрати на створення та синхронізацію потоків (наприклад, N >= 10^8 або складні математичні обчислення на кожній ітерації).

4. Відповіді на контрольні питання

1. Що таке thread? Це найменша одиниця виконання в межах процесу, яка має власний лічильник команд, регістри та стек, але поділяє ресурси процесу з іншими потоками.
2. Чим thread відрізняється від process? Процес має ізольований адресний простір і власні ресурси ОС, тоді як потоки існують усередині процесу та спільно використовують його адресний простір і відкриті файли.
3. Що threads одного process поділяють? Сегмент коду (.text), глобальні та статичні змінні (.data, .bss), динамічну пам'ять (heap), дескриптори відкритих файлів, PID процесу.
4. Що кожен thread має власне? Ідентифікатор потоку (TID), набір регістрів процесора (включно з вказівником інструкцій RIP та вказівником стеку RSP), власний стек викликів і маску сигналів.
5. Чи має кожен thread власний stack? Так, кожному потоку виділяється окрема область пам'яті під стек.
6. Чи мають threads спільний heap? Так, динамічна пам'ять, виділена через malloc(), доступна всім потокам процесу за відповідним вказівником.
7. Для чого використовується pthread_create()? Для створення нового потоку в поточному процесі та запуску в ньому вказаної стартової функції.
8. Для чого використовується pthread_join()? Для очікування завершення вказаного потоку та отримання його значення, що повертається.
9. Чи гарантується порядок виконання threads порядком pthread_create()? Ні, порядок визначається планувальником ОС (scheduler).
10. Чим concurrency відрізняється від parallelism? Concurrency (конкурентність) — це структура програми, де кілька задач можуть виконуватися з перекриттям у часі (навіть на одному ядрі через перемикання контексту). Parallelism (паралелізм) — це фізично одночасне виконання кількох задач на різних ядрах процесора.
11. Що таке shared state? Дані в пам'яті (глобальні змінні, об'єкти в heap), до яких мають доступ одночасно кілька потоків.
12. Що таке race condition? Ситуація, коли коректність роботи програми залежить від неконтрольованого порядку та таймінгу виконання інструкцій кількома потоками при доступі до спільних даних.
13. Що таке lost update? Втрата результату модифікації змінної одним потоком через те, що інший потік прочитав застаріле значення до запису першого і перезаписав його своїм результатом.
14. Чому counter++ не слід вважати atomic? Бо на рівні CPU ця операція складається з трьох окремих кроків (зчитування з пам'яті, додавання в регістрі, запис у пам'ять), між якими потік може бути перерваний.
15. Що таке critical section? Ділянка коду, яка звертається до спільних ресурсів і не повинна виконуватися більш ніж одним потоком одночасно.
16. Що таке mutual exclusion? Властивість синхронізації, яка гарантує, що в критичній секції в будь-який момент часу перебуває не більше одного потоку.
17. Що таке mutex? Об'єкт синхронізації (mutual exclusion lock), який використовується потоками для ексклюзивного доступу до критичної секції.
18. Що робить pthread_mutex_lock()? Захоплює м'ютекс, якщо він вільний, або переводить потік у стан очікування, доки власник не звільнить його.
19. Що відбувається, якщо mutex уже належить іншому thread? Потік, що викликав pthread_mutex_lock(), блокується планувальником ОС і чекає, поки м'ютекс не буде розблоковано.
20. Навіщо викликати pthread_mutex_unlock()? Щоб звільнити критичну секцію і дозволити іншим очікуючим потокам отримати доступ до спільного ресурсу (інакше виникне deadlock).
21. Чому надто велика critical section може погіршити concurrency? Бо інші потоки змушені довго простоювати в очікуванні звільнення замка, що перетворює паралельне виконання на послідовне.
22. Що таке lock contention? Стан високої конкуренції, коли багато потоків одночасно намагаються захопити один і той самий м'ютекс і витрачають час на очікування.
23. Чому більше threads не обов'язково означає більшу performance? Через накладні витрати на створення потоків, перемикання контексту, синхронізацію та боротьбу за спільні ресурси (lock contention і кеш-промахи).
24. Що таке deadlock? Стан взаємного блокування, коли два або більше потоків назавжди зупиняються, очікуючи звільнення ресурсів, які утримують інші учасники цього ж циклу.
25. Чим deadlock відрізняється від race condition? При race condition потоки продовжують працювати, але псують дані; при deadlock потоки повністю зупиняються і програма зависає.
26. Що таке circular wait? Циклічне очікування — умова deadlock, коли існує замкнений ланцюжок потоків, де кожен чекає на ресурс, утримуваний наступним потоком у ланцюжку.
27. Як однаковий порядок отримання locks може допомогти уникнути deadlock? Глобальне впорядкування блокувань (наприклад, завжди спочатку mutex1, потім mutex2) робить утворення замкненого циклу очікування математично неможливим.
28. Що таке starvation? Ситуація, коли потік тривалий час або ніколи не отримує необхідний ресурс чи процесорний час через те, що інші потоки постійно перехоплюють його першими.
29. Чому local accumulation у parallel_sum кращий за shared counter із mutex на кожній iteration? Бо локальні суми обчислюються на власних стеках потоків без блокувань, а об'єднання відбувається лише один раз наприкінці замість мільйона операцій блокування.
30. Чому успішні 100 запусків concurrent program не доводять відсутність race condition? Оскільки перемикання потоків планувальником є недетермінованим, помилковий збіг таймінгів може проявитися на 101-му запуску або при іншому навантаженні на систему.

---

5. Висновок
У ході лабораторної роботи було експериментально досліджено багатопотокове програмування на C із використанням POSIX Threads. Підтверджено, що потоки одного процесу поділяють глобальні дані та динамічну пам'ять (heap), але мають власні незалежні стеки. На практиці відтворено ефект race condition і втрату оновлень при несинхронізованому інкременті, усунуто цю проблему за допомогою pthread_mutex_t, досліджено накладні витрати на синхронізацію та механізм виникнення deadlock. Реалізація parallel_sum довела, що найефективнішим способом побудови паралельних програм є мінімізація спільного змінюваного стану за рахунок локального накопичення результатів у кожному потоці.
